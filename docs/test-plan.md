# Beam Streaming POC 测试计划与用例设计

本文档详细规划了基于 Pub/Sub 的 Apache Beam 窗口（Windowing）与水位线（Watermark）机制的测试用例。通过向 Pub/Sub 注入具有特定 `event_timestamp` 的数据，来精确验证系统在不同场景下的行为。

---

## 1. 测试基础策略

- **时间推进器 (Watermark Advancer)**:
  Pub/Sub 模式下，Beam 的 Watermark 是基于接收到消息的事件时间启发式推算的。为了让窗口如期闭合，我们在测试脚本中会定期发送包含最新时间的“心跳消息”或不同账号的正常消息，以强制系统认为“旧的时间点已经安全通过”，从而触发窗口计算。
- **自定义时间戳注入**:
  所有的测试消息在发布至 Pub/Sub 时，必须在 Attributes 中携带 `event_timestamp`（Unix 毫秒级时间戳）。

---

## 2. 测试用例设计

### 剧本 1：固定窗口 (Fixed Window) —— "整点大盘冲刺"

**测试目标**: 验证非重叠窗口（30秒）的精确划分、跨窗口金额清零以及超额报警。

**参数配置**:
- 窗口大小: 30s
- 报警阈值: 100K (Yellow)

**数据注入序列**:
1. `[12:00:05]` 发送 `$40K` (账号 A)
2. `[12:00:15]` 发送 `$70K` (账号 A)  *(此时 A 累计 $110K，预期将触发报警)*
3. `[12:00:25]` 发送 `$50K` (账号 B)
4. `[12:00:35]` 发送 `$10K` (账号 A)  *(强行推进 Watermark 越过 12:00:30，并进入下一个窗口)*

**预期结果**:
- **触发 1**: 窗口 `[12:00:00 - 12:00:30)` 闭合，输出 账号 A: $110K (🟡 Yellow Alert), 账号 B: $50K。
- **触发 2**: 随着时间推进，下一个窗口 `[12:00:30 - 12:01:00)` 闭合时，账号 A 的金额应重新从 $10K 算起，无报警。

---

### 剧本 2：滑动窗口 (Sliding Window) —— "持续暴露的高额敞口"

**测试目标**: 验证同一笔交易如何被纳入多个重叠的窗口中，引发连续暴露风险报警。

**参数配置**:
- 窗口大小: 30s
- 滑动步长: 10s
- 报警阈值: 100K (Yellow)

**数据注入序列**:
1. `[12:00:10]` 发送 `$150K` (账号 A) *(一笔直接超限的超级大单)*
2. `[12:00:25]` 发送心跳数据 (账号 B, $1K)
3. `[12:00:35]` 发送心跳数据 (账号 B, $1K)
4. `[12:00:45]` 发送心跳数据 (账号 B, $1K)
5. `[12:00:55]` 发送心跳数据 (账号 B, $1K)

**预期结果**:
- 窗口 `[12:00:00 - 12:00:30)` 闭合: 输出 账号 A $150K (🟡 报警 1)
- 窗口 `[12:00:10 - 12:00:40)` 闭合: 输出 账号 A $150K (🟡 报警 2)
- 窗口 `[12:00:20 - 12:00:50)` 闭合: 账号 A $150K 大单已滑出窗口，无报警输出。

---

### 剧本 3：会话窗口 (Session Window) —— "突击洗钱模拟"

**测试目标**: 验证无固定周期的会话窗口，能够根据交易间隙（Gap Duration）自动合并和切分用户的活跃周期。

**参数配置**:
- 会话间隙 (Gap Duration): 15s
- 报警阈值: 100K (Yellow)

**数据注入序列**:
1. `[10:00:01]` 发送 `$40K` (账号 C)
2. `[10:00:10]` 发送 `$40K` (账号 C) *(间隙 9s < 15s，合并入当前 Session)*
3. `[10:00:20]` 发送 `$30K` (账号 C) *(间隙 10s < 15s，继续合并，累计 $110K 触发阈值)*
4. `[10:00:35]` 发送心跳数据 (账号 B) *(用来推进 Watermark 过 10:00:35，结束账号 C 的第一个 Session)*
5. **故意停顿**，模拟用户停止交易。
6. `[10:00:45]` 发送 `$20K` (账号 C) *(间隙 25s > 15s，开辟全新 Session)*
7. `[10:01:10]` 发送心跳数据 (账号 B) *(推进 Watermark)*

**预期结果**:
- **会话 1**: 输出 `[10:00:01 - 10:00:35)` (开始时间至最后一条记录+15s)，累计 $110K (🟡 Yellow Alert)。
- **会话 2**: 输出 `[10:00:45 - 10:01:00)`，累计 $20K，正常状态。

---

### 剧本 4：水位线与迟到数据 (Watermark & Late Data) —— "姗姗来迟的纽约交易"

**测试目标**: 验证 Allowed Lateness 配置，观察过期窗口被重算，以及晚于宽限期的数据被丢弃的过程。

**参数配置**:
- 窗口大小: 30s (Fixed Window)
- Allowed Lateness (允许迟到): 60s
- 报警阈值: 100K (Yellow)

**数据注入序列**:
1. **正常累积**:
   - `[12:00:10]` 发送 `$50K` (HK, 账号 A)
   - `[12:00:20]` 发送 `$40K` (SG, 账号 A) *(累计 $90K)*
2. **强制推线**:
   - `[12:00:35]` 发送心跳数据 (HK, 账号 B)。此举将 Watermark 推过 12:00:30，导致第一个窗口闭合。
   - *(预期中间态: 窗口 `[12:00:00 - 12:00:30)` 首次输出，结果 $90K，无报警)*
3. **迟到数据 (宽限期内)**:
   - `[12:00:40]` (物理时间)，收到一笔发生于 `[12:00:25]` 的纽约交易 (US, 账号 A, `$20K`)。
   - 迟到 15s，但在 60s 宽限期内。
   - *(预期结果: Beam 自动重算旧窗口，追加输出 $110K 并触发 🟡 报警，附带 "Late Data" 标记)*
4. **极度迟到数据 (宽限期外)**:
   - `[12:02:00]` (物理时间)，收到一笔发生于 `[12:00:28]` 的交易 (US, 账号 A, `$50K`)。
   - 这笔交易落后 Watermark 超过 60s (Allowed Lateness)。
   - *(预期结果: Beam 直接丢弃该数据，不再输出更新，但在自定义的 `late_data_log` PTransform 中应能捕捉并记录到数据库)*。

---

## 3. 执行要求

为了确保上述测试顺畅执行：
1. **Publisher 脚本必须具备精确构造时间戳的能力**。
2. 由于 Pub/Sub 是异步的，Publisher 在发送紧随其后的“越界”心跳数据时，最好物理上 `sleep(1-2)` 秒，防止因为乱序导致本来要滞后的数据先到了。
3. Beam 流处理端需设置合适的 Trigger (例如 `AfterWatermark.pastEndOfWindow().withLateFirings()`)，以确保能输出迟到的更新。
